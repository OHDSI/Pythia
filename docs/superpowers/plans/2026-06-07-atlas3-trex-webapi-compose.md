# Atlas3 + trex-embedded-WebAPI Compose — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a single Docker Compose stack to the `trex-dx` repo that runs the Atlas3 frontend with the pythia (bao) AI agent, served by trex's embedded WebAPI (a DuckDB extension) instead of the upstream `ohdsi/webapi` image, in a single-node trex setup.

**Architecture:** Pull the published `ghcr.io/ohdsi/trexsql:latest` image as a single trex node (`data_node` + `trexas` + `pgwire`). A one-shot init container triggers `LOAD webapi; SELECT webapi_start();` over pgwire, booting OHDSI WebAPI (incl. bao endpoints) on port 8080 inside the trex process. The Atlas3 frontend is built locally with `VITE_BAO_AGENT_ENABLED=true` and reverse-proxies `/WebAPI/*` to the trex node. A preloaded `ohdsi/broadsea-atlasdb` Postgres backs WebAPI; a plain `postgres:16` backs trex's own metadata.

**Tech Stack:** Docker Compose, `ghcr.io/ohdsi/trexsql:latest`, `ohdsi/broadsea-atlasdb:2.3.0`, `postgres:16`, Caddy/Vite (Atlas3 frontend), psql, AWS Bedrock (bao).

**Spec:** `docs/superpowers/specs/2026-06-07-atlas3-trex-webapi-compose-design.md`

**Verification model:** This is infrastructure — "tests" are `docker compose` lifecycle commands, container health, and HTTP/SQL probes. The two highest-risk unknowns (does the published image bundle the WebAPI artifacts; does `webapi_start()` boot over pgwire) are verified in Tasks 1 and 4 before later work depends on them.

**Conventions used throughout:**
- Compose file: `docker-compose.atlas3-trex.yml` (repo root).
- Shorthand: `export DC="docker compose -f docker-compose.atlas3-trex.yml"` — every `$DC` below assumes this is set in your shell.
- `POSTGRES_PASSWORD` and the pgwire password are both `mypass` for local dev.

This task de-risks the whole plan. If the published image lacks `webapi.trex` or `libwebapi-native.so` for your host arch, STOP and escalate (the fallback is building the trex image from `../trex` via `Dockerfile.native-lib`, which reopens the "pull vs build" decision — out of scope for this plan).

**Files:** none (investigation only).

- [ ] **Step 1: Pull the image**

Run:
```bash
docker pull ghcr.io/ohdsi/trexsql:latest
```
Expected: pull completes; a digest is printed.

- [ ] **Step 2: Check for the webapi extension and native lib inside the image**

Run:
```bash
docker run --rm --entrypoint sh ghcr.io/ohdsi/trexsql:latest -c \
  'echo "--- .trex extensions ---"; find /usr/lib/trexsql/extensions -name "webapi*.trex" 2>/dev/null; \
   echo "--- native lib ---"; find / -name "libwebapi-native.so" 2>/dev/null; \
   echo "--- LD_LIBRARY_PATH ---"; echo "$LD_LIBRARY_PATH"; ldconfig -p 2>/dev/null | grep -i webapi'
```
Expected: at least one `webapi*.trex` path AND a `libwebapi-native.so` path are printed. The `.so` should sit on `LD_LIBRARY_PATH` (commonly `/usr/local/lib` or `/usr/lib`).

- [ ] **Step 3: Record the findings and decide**

If both artifacts are present: note their exact paths in your working notes (you may need `WEBAPI_NATIVE_LIB=<path>` in Task 3 if the `.so` is NOT on `LD_LIBRARY_PATH` under its default name `libwebapi-native.so`). Proceed.

If either is missing: STOP. The published `:latest` does not support embedded WebAPI on this arch. Escalate to the user — building the image from `../trex` is a scope change.

### Task 4: Boot the embedded WebAPI via a one-shot init container (GATING)

Verifies risks #2 (env pickup), #5 (pgwire permits LOAD/start), and that WebAPI binds :8080 inside the trex process.

**Files:**
- Modify: `docker-compose.atlas3-trex.yml` (add `webapi-start` service)

- [ ] **Step 1: Manually prove the boot path before automating it**

With the stack from Task 3 still up, exec a psql client against trex's pgwire and trigger the boot:
```bash
export DC="docker compose -f docker-compose.atlas3-trex.yml"
$DC exec trex sh -c 'PGPASSWORD=mypass psql -h 127.0.0.1 -p 5432 -U trex -d main -c "LOAD webapi;" -c "SELECT webapi_start();"'
```
Expected: `LOAD` succeeds and `webapi_start()` returns a status row (e.g. `running`/`starting`). If you get an auth error, the pgwire password isn't `mypass` — check `SELECT * FROM trex_pgwire_status();` and the `password` in `SWARM_CONFIG`; the username may differ from `trex` (try `-U postgres`). Resolve before continuing.

- [ ] **Step 2: Probe the WebAPI port**

Run (poll up to ~60s — Spring context takes time):
```bash
for i in $(seq 1 30); do
  code=$($DC exec -T trex sh -c 'curl -s -o /dev/null -w "%{http_code}" http://localhost:8080/WebAPI/info' 2>/dev/null)
  echo "WebAPI/info: $code"; [ "$code" = "200" ] && break; sleep 5
done
curl -s -o /dev/null -w "host WebAPI/info: %{http_code}\n" http://localhost:8080/WebAPI/info
```
Expected: `WebAPI/info: 200` inside the container AND `host WebAPI/info: 200` (published port works). If `webapi_start()` ran but `/info` never returns 200, inspect `$DC logs trex` for Spring/datasource errors — if it complains about missing datasource config, this is risk #2: add `SPRING_APPLICATION_JSON` to the trex env (see fallback in Step 5) and re-run from Task 3 Step 3.

- [ ] **Step 3: Add the `webapi-start` one-shot service**

Append to `docker-compose.atlas3-trex.yml` under `services:` (after `trex`):
```yaml
  # One-shot: boots the embedded WebAPI by loading the extension and calling
  # webapi_start() over trex's pgwire port. Completes once /WebAPI/info is 200.
  webapi-start:
    image: postgres:16-alpine
    depends_on:
      trex:
        condition: service_healthy
    environment:
      PGPASSWORD: ${POSTGRES_PASSWORD:-mypass}
    entrypoint:
      - sh
      - -c
      - |
        set -e
        echo "[webapi-start] LOAD webapi; SELECT webapi_start();"
        psql -h trex -p 5432 -U trex -d main -c "LOAD webapi;" -c "SELECT webapi_start();"
        echo "[webapi-start] waiting for http://trex:8080/WebAPI/info"
        for i in $$(seq 1 60); do
          code=$$(wget -q -O /dev/null -S "http://trex:8080/WebAPI/info" 2>&1 | awk '/HTTP\//{print $$2; exit}')
          echo "  attempt $$i: $$code"
          [ "$$code" = "200" ] && { echo "[webapi-start] WebAPI is up"; exit 0; }
          sleep 5
        done
        echo "[webapi-start] WebAPI did not come up in time" >&2
        exit 1
    restart: "no"
```
NOTE: if Step 1 showed a different pgwire user, change `-U trex` accordingly here.

- [ ] **Step 1: Add the `atlas3-frontend` service**

Append under `services:`. Build context is `../Atlas3` (the one external build dependency — Atlas3 must be checked out alongside trex-dx). The vendored `./Caddyfile` is mounted over the image's copy; `WEBAPI_HOST=trex` points the proxy at the trex node.
```yaml
  # Atlas3 Caddy/Vite UI, built locally so VITE_BAO_AGENT_ENABLED is baked in.
  atlas3-frontend:
    build:
      context: ../Atlas3
      dockerfile: Dockerfile
      args:
        VITE_AUTH_ENABLED: "true"
        VITE_AUTH_SKIP_LOGIN: "false"
        VITE_AUTH_PROVIDERS: '[{"name":"Database","url":"user/login/db","ajax":true,"icon":"mdi-database","isUseCredentialsForm":true}]'
        VITE_BAO_AGENT_ENABLED: ${VITE_BAO_AGENT_ENABLED:-true}
    platform: linux/amd64
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - atlas3-caddy-data:/data
    environment:
      WEBAPI_HOST: trex
      WEBAPI_PORT: "8080"
      WEBAPI_URL: ${WEBAPI_URL:-https://localhost/WebAPI}
      CADDY_HOSTNAME: ${CADDY_HOSTNAME:-localhost}
      CADDY_TLS_DIRECTIVE: ${CADDY_TLS_DIRECTIVE:-tls internal}
    depends_on:
      atlas3-db-init:
        condition: service_completed_successfully
```

- [ ] **Step 2: Build and start the frontend**

```bash

# trex-dx

Docker Compose stack running the **Atlas3** frontend with the **pythia** (bao)
AI agent, served by **trex's embedded WebAPI** (a DuckDB extension) instead of
the upstream `ohdsi/webapi` image. Single-node trex.

## Prerequisites

- Docker + Docker Compose.
- The `Atlas3` repo checked out as a sibling directory (`../Atlas3`) — the
  frontend is built from it locally so the pythia FAB is baked in.
- An AWS Bedrock long-term API key for pythia.

## Setup

```bash
cp .env.example .env
# Edit .env: set AWS_BEARER_TOKEN_BEDROCK (required for pythia),
# optionally BAO_AGENT_MODEL and POSTGRES_PASSWORD.

docker compose -f docker-compose.atlas3-trex.yml up -d --build
```

- UI: https://localhost/atlas/ (self-signed cert; accept the warning).
- WebAPI: https://localhost/WebAPI/info (proxied to the trex node's :8080).

## How it works

`trex-init` generates `./secrets/` (gitignored). `postgres` backs trex's
metadata; `ohdsi/broadsea-atlasdb` backs the OHDSI WebAPI. The single `trex`
node runs trexas + pgwire and hosts the embedded WebAPI. `webapi-start` boots
it via `LOAD webapi; SELECT webapi_start();` over pgwire; `atlas3-db-init`
loads sources/users; `atlas3-frontend` serves Atlas and proxies `/WebAPI/*` to
the trex node.

See `docs/superpowers/specs/` and `docs/superpowers/plans/` for design details.
```
